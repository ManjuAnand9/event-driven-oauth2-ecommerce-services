Request Lifecycle

Order placement workflow

Checkout combines authenticated client requests, synchronous service calls, database persistence and asynchronous event publication.

01

User initiates checkout

React sends the order request through the API Gateway using the authenticated session.

React → API Gateway
02

Customer identity is resolved

The authenticated user's email is resolved against Customer Service to obtain the application customer ID.

JWT Email → Customer Service → customerId
03

Order Service calls downstream services

Required customer and product information is retrieved through synchronous service-to-service REST calls.

Order → Customer / Product
04

Order is persisted

The final order state is stored in Order Service's independently owned PostgreSQL database.

Order Service → Order DB
05

Kafka event is published

Order creation publishes an ORDER_CREATED event for independently running consumers.

Order Service → Kafka → ORDER_CREATED
06

Client receives order ID

React receives the successful OrderResponse and presents the unique order identifier to the customer.

OrderResponse.orderid → React
Distributed Communication

Synchronous + asynchronous communication

Communication style is selected according to whether the caller requires an immediate downstream response.

↔

Synchronous REST

Used for request paths where Order Service requires downstream data before completing the operation.

Asynchronous Kafka

Object Storage

Private S3 image workflow

Product images stay in a private bucket while temporary presigned URLs allow controlled browser uploads and reads.

01

Request presigned upload URL

React asks Product Service for a temporary S3 upload URL.

React → Product Service → S3 Presigner
02

Browser uploads directly to S3

Product image bytes do not need to pass through Product Service.

Browser → Presigned PUT → S3
03

Store image key

Product Service persists the stable object key rather than a temporary signed URL.

imageKey → Product DB
04

Generate temporary GET URL

Product APIs generate a fresh presigned image URL when product information is requested.

imageKey → Presigned GET → Browser

Engineering Decisions

Why the system is designed this way

Why Kafka?

Event consumers should not increase the latency or coupling of the synchronous order creation path.

Why database per service?

Independent persistence reduces direct data coupling and preserves clear service ownership.

Why presigned S3 URLs?

Large image payloads can move directly between the browser and object storage while the bucket stays private.

Why API Gateway?

The client receives one entry point while internal services remain independently addressable and protected.

Why synchronous REST?

Some workflows require immediate downstream data before the caller can safely complete its request.

Why OAuth2/JWT?

Stateless access tokens allow authenticated requests to propagate identity and authorization claims.
